## Explicit remaining risks and follow-up

1. **Parent credentials still appear in URLs and browser storage.** Printed QR/PIN links, `/parents/[pin]`, recovery redirects, legacy favorites GET requests and other API query strings still carry PINs and/or email addresses. The gallery's new JSON POST favorites reads remove credentials from those request URLs only. Checkout still explicitly supplies PIN/email-bearing success and cancel URLs to Stripe. Favorites/wall-ratio local-storage keys and combined-cart session storage retain these values too. The new proof cookie is a rate-budget proof, not a replacement parent session. `no-referrer` reduces outbound referrer leakage but cannot erase browser history, copied links, screenshots, provider/server URL logs, browser storage, or explicitly supplied checkout return URLs. A separately tested QR/PIN bootstrap into a short-lived HttpOnly parent session, followed by URL/query removal and migration of browser storage and checkout returns, remains an architecture change. Printed labels must remain reusable; individual bootstrap exchanges can be short-lived or consumed once, and saved carts must continue working. These observations establish where credentials are handled, not evidence of attacker access.
   A reviewed checkout-only migration would require a short-lived server-side return handoff bound to a host-only HttpOnly browser cookie, exact owner/order-group/return-lane context, and the original viewer identity. It must be persisted and reused under the existing payment lock before creating Stripe sessions, preserving idempotent retries. A clean return page must render resolved gallery context in memory; merely reconstructing the existing PIN URL moves the disclosure. New-session confirmation must enforce the same cookie.
